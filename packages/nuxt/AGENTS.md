# @vunset/nuxt

A Nuxt module registering `@vunset/vue`'s and `@vunset/ui`'s components and
composables. `src/components.ts` is generated by `scripts/components.ts` (run by
its `build`) from the packages' entries. Code that runs in the app sits in
`src/runtime/`, added with `addPlugin`.

## Decisions

- **Registration** comes from a list `scripts/components.ts` writes from the
  entries (`export { default as X } from '….vue'`, plus `Part`), not
  `addComponentExports`, which would register every export, constants too. A
  test fails when the list is stale. Priority `-1`: an app's own component of
  the same name wins. The chart and data-table entries need their peers
  resolvable.
- **Resolution.** Our packages resolve from the module itself, the peers from
  the app's roots. Each export gets an alias, longest key first: Vite and Nitro
  take the first match, and a bare name prefix-matches its subpaths.
- **Icons.** The `icons` option adds `runtime/icons.ts`, a plugin calling
  `configureIcons`: the sprite through `runtimeConfig.public.vunset`, the
  folders through a template (`#vunset/icons`), since `import.meta.glob` takes
  no variable. The template is virtual, so the glob starts with `/` (Vite's
  root, `srcDir`). `spriteDir` builds a sprite (`src/sprite.ts`, on
  `parseInlineSvg` from utils) into `buildDir`, a Nitro public asset, written on
  `build:before`: the CLI empties `buildDir` after `nitro:config`. Rebuilt on
  `builder:watch`, so a folder outside the app's watched dirs isn't. The sprite
  path goes into runtime config as a value: `undefined` comes out as `''`,
  which reads as no sprite.
- **`#app` in `runtime/`**, never `nuxt/app`: the alias is the app's own Nuxt,
  where a package path would resolve from wherever the file lives (a linked
  repo's own `nuxt`, a second copy). The tsconfigs map `#app` to Nuxt's types.
- **Toasts and SSR.** `useToast()` and the viewport take a store
  `provideToastStore` provided (to a component, or an app) before the shared
  one; outside a component it is always the shared one. `runtime/toasts.ts`
  provides a fresh store per server request and carries its toasts, as plain
  data, through `useState` into the client's *shared* store, so a plain
  module's `useToast()` reaches the same toasts there. Generated ids skip ones
  already showing, since the server's are carried in.
- **Testing in an app.** A client-only app (`ssr: false`) can link the
  packages: `"@vunset/vue": "file:<repo>/packages/vue"` for each of utils,
  vue, ui, nuxt, plus `vite.server.fs.allow: ['<repo>']`, or `all.css` is
  refused with a 403. Run `npm run build:lib` in the repo; the module keeps
  linked packages out of Vite's pre-bundling, so a rebuild of vue, ui or utils
  shows on reload. A change to this module needs the dev server stopped and
  started: touching `nuxt.config` restarts Nuxt in the same process, which
  keeps the module it imported. With SSR, link nothing: install packed tarballs
  (`npm pack` each, with `overrides` for utils and vue), since a linked
  package's `vue` resolves from the repo and the server gets two.
